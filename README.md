# Aave V3 Multi-Chain Monitor

A small always-on service that watches Aave V3 reserves across one or more
chains directly over RPC -- no third-party indexer, no subgraph -- and
pushes Telegram alerts when something worth knowing about happens.

## What it watches

| Category | Trigger |
|---|---|
| Reserve lifecycle | A reserve is onboarded or removed from the pool |
| Reserve configuration | Active / frozen / paused / borrowing-enabled flags flip |
| Utilization | Utilization crosses the interest-rate model's optimal point (the "kink") |
| Supply | Total supply moves by more than a configurable % since the last check |
| Interest-rate model | Optimal ratio, base rate, or either slope changes -- ships with a before/after rate-curve chart |

When a **supply** or **utilization** alert fires, the monitor additionally
pulls the five largest `Supply` / `Withdraw` / `Borrow` / `Repay` /
`LiquidationCall` events since the last check and attaches them to the
alert, so you're not just told *that* utilization moved but *what caused
it*. Activity logs are never indexed continuously -- `eth_getLogs` is only
called after a threshold has actually fired.

## Project layout

```
main.py                    entry point
constants.py                ABIs, RAY, bit positions (yours, not touched by this repo)
config.json                  your chains/thresholds -- gitignored, may reference ${secrets}
config.example.json          template to copy from
secret.key                    encryption key -- gitignored, generated by setup
secrets.enc.json              encrypted secret values -- gitignored, generated by setup
state.json                    persisted per-reserve state -- gitignored
aave_monitor/                 the package (see below)
scripts/
  setup.py                    first-time interactive setup
  update_secret.py             update/add one secret
  help.py                      command reference
```

Inside `aave_monitor/`, each module owns one concern: `web3_client.py`
(RPC + contract wiring), `events.py` (activity log fetch/decode),
`rate_model.py` / `charts.py` (interest-rate model math + chart),
`asset_monitor.py` (the per-reserve check, ties everything together),
`chain_monitor.py` / `app.py` (orchestration + the main loop), and
`secrets_store.py` (encryption -- see below).

## Setting up on a Raspberry Pi 4 (8GB) + 32GB microSD

Your hardware is comfortably enough for this: the workload is a handful of
RPC calls every 30 minutes, not something CPU- or RAM-hungry. 32GB is
plenty of headroom even once Docker images and a local LLM are added later
-- just avoid also using this card for heavy logging/video work.

**1. Flash the OS**

Use [Raspberry Pi Imager](https://www.raspberrypi.com/software/). Choose
**Raspberry Pi OS Lite (64-bit)** -- no desktop needed for a headless
server, and 64-bit matters because you'll want arm64 Docker images later.
In the Imager's gear/settings icon before writing:
- Set hostname (e.g. `aave-monitor`)
- Enable SSH, set a password or paste your public key
- Configure Wi-Fi if not using Ethernet (Ethernet is more reliable for an
  always-on service)

**2. First boot & basic hardening**

```bash
ssh pi@aave-monitor.local          # or its IP
sudo apt update && sudo apt full-upgrade -y
sudo raspi-config                  # optional: expand filesystem, set locale/timezone
sudo apt install -y git vim ufw
sudo ufw allow ssh
sudo ufw enable
sudo reboot
```

Since this device won't run a desktop or anything that needs inbound
connections besides SSH, a default-deny firewall with only SSH open is a
sensible baseline.

**3. Install Docker**

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker $USER
newgrp docker                      # or log out/in
docker compose version             # confirm the compose plugin is present
```

**4. Clone and set up the project**

```bash
git clone <your-repo-url> lendingMarketsRiskMonitor
cd lendingMarketsRiskMonitor
python3 -m venv venv && source venv/bin/activate   # only needed if running bare-metal too
pip install -r requirements.txt
```

Then, depending on whether `config.json` already exists with real values in
it or you're starting fresh:

```bash
python scripts/setup.py             # fresh install: builds config.json from the example
# -- or --
python scripts/migrate_secrets.py   # already have a config.json with real secrets in it
```

`setup.py` creates `config.json` from `config.example.json` if it doesn't
exist, generates `secret.key`, and interactively prompts you for the
Telegram bot token, chat id, and any RPC API keys your `config.json`
references. `migrate_secrets.py` is for the opposite case -- a
`config.json` you already had working, with real secrets sitting in it as
plaintext -- it extracts them, encrypts them, and rewrites `config.json`
to reference them as `${placeholders}` instead (backing up the original to
`config.json.bak` first). Nothing you type into either script is echoed to
the terminal or written to shell history.

**5. Run it**

```bash
docker compose up -d --build
docker compose logs -f
```

That's the whole deployment. `restart: unless-stopped` in
`docker-compose.yml` means it survives reboots and crashes without any
systemd unit needed on your end.

## Should you use Docker?

**Yes**, for the reasons you already identified plus one more:

- **Isolation for the LLM.** Once you add a local LLM container tomorrow,
  Docker keeps it from sharing a Python environment, port space, or
  filesystem with this monitor. If the LLM container gets compromised or
  just misbehaves (LLM serving stacks pull in a lot of dependencies), it
  can't reach into this service's process or files.
- **Resource limits.** `docker-compose.yml` already caps this service at
  512MB so a future LLM container (which will want several GB) can't starve
  it, and vice versa.
- **Reproducibility.** "Works on my Pi" stops being a question -- the image
  pins Python and dependency versions, so a fresh SD card gets you back to
  a known-good state in one `docker compose up`.
- **Clean secret handling.** `config.json`, `secret.key`, and
  `secrets.enc.json` are bind-mounted read-only or read-write as
  appropriate rather than baked into the image (see `.dockerignore`), so
  they never end up inside a Docker image layer that could be pushed
  somewhere by mistake.

The cost is small: a bit more RAM/disk overhead and one extra layer to
reason about when debugging. For a device you're about to turn into a
small multi-service host, that trade is worth it.

## Secrets: how the encryption works

**Why not bcrypt:** bcrypt is a one-way password hash -- it's designed so
you can *verify* a password was typed correctly, but you can never get the
original value back out. That's the wrong tool here: the monitor needs the
actual Telegram bot token to call Telegram's API, so it must be
recoverable. This repo uses
[`cryptography`](https://cryptography.io/)'s `Fernet` instead --
reversible symmetric (AES) encryption, which is the standard choice for
"encrypt this now, decrypt it at runtime."

**How it fits together:**

1. `python scripts/setup.py` generates `secret.key` -- a random 32-byte
   key, written with `chmod 600` (owner-only) permissions.
2. `config.json` doesn't hold secrets directly. Instead it uses
   placeholders:
   ```json
   {
     "telegram_bot_token": "${telegram_bot_token}",
     "telegram_chat_id": "${telegram_chat_id}",
     "chains": {
       "ethereum": {
         "rpc_url": "https://eth-mainnet.g.alchemy.com/v2/${alchemy_api_key}",
         "pool_address": "0x87870Bca3F3fD6335C3F4ce8392D69350B4fA4E2"
       }
     }
   }
   ```
3. `setup.py` scans `config.json` for every `${name}` placeholder, prompts
   you for each value, encrypts it, and stores it in `secrets.enc.json` as
   `{"telegram_bot_token": "<ciphertext>", ...}`.
4. At runtime, `load_config()` decrypts everything with `secret.key` and
   substitutes the placeholders in memory. The plaintext values never touch
   disk.
5. To change one secret later, without re-running the whole setup:
   ```bash
   python scripts/update_secret.py telegram_bot_token
   ```

**Being honest about the threat model:** this stops secrets from leaking
via `git`, backups, or someone browsing the SD card without `secret.key`.
It does *not* protect against someone who can already read files as the
same OS user the monitor runs as (they could just read `secret.key` too),
or against root on the Pi. For a single-user Pi that's a reasonable,
honestly-scoped bar -- it's not pretending to be a hardware security
module.

**Make sure these are in `.gitignore`** (add if not already there):
```
secret.key
secrets.enc.json
state.json
config.json
```

**Back up `secret.key` somewhere outside the repo** (a password manager is
fine). If you lose it, every stored secret becomes permanently
undecryptable and you'll need to re-run `setup.py` from scratch.

## Command reference

Run `python scripts/help.py` any time, or see the table below.

| Command | What it does |
|---|---|
| `python scripts/setup.py` | First-time setup: config, key, secrets (fresh config) |
| `python scripts/migrate_secrets.py` | Already have a config.json with real secrets in plaintext? Encrypts them and rewrites config.json to use placeholders |
| `python scripts/update_secret.py [name]` | Update or add one secret |
| `docker compose up -d --build` | Build and run in the background |
| `docker compose logs -f` | Follow logs |
| `docker compose down` | Stop |
| `python main.py` | Run directly (bare-metal / venv) |
